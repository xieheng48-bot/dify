# 怎么读、怎么写这份项目代码

先记住一个分工：**页面收集意图，API 校验身份和参数，Service 作业务决定，SQLite 保存证据；模型只负责解释。** 不要先背 Dify 或 LangChain 名词，从一次“我要退货”的真实调用读起。

## 第一遍：用 20 分钟顺着调用链阅读

1. 启动服务，在首页选择 Alice，订单填 A1001，点击“查看并核验”。浏览器请求 `POST /api/returns/check`，请求体只含订单编号。
2. 打开 `commerce_app/api.py`。先看 `create_app()`：它组织配置、数据库、Service 和路由。然后读内部 `user()`：Bearer token 映射到服务端身份，不能信任前端传一个 `user_id`。
3. 找到 `check()`。这一层把已经校验的参数和身份传给 `CommerceService.eligibility()`，没有把 SQL 或退货规则塞进路由。
4. 打开 `commerce_app/service.py`。`_order()` 使用 `id=? AND user_id=?` 绑定查询，拿不到时统一返回“不存在或不属于当前用户”。`_eligibility()` 在这之后读取订单品类和签收日，筛选恰好一个适用政策，计算签收天数，再返回 `eligible`、原因和引用。
5. 点击“生成待确认申请”。路由 `propose()` 调用 Service 的 `propose()`，后者核验资格，产生申请 ID、15 分钟有效期、随机确认凭据和快照摘要，只存 `proposals`，还没有 `tickets`。
6. 页面通过 `human_preview()` 读取需要人核对的快照，显示政策、订单和原因。用户勾选后才发送 `POST /api/human/confirm`。
7. Service 的 `confirm()` 开启 `BEGIN IMMEDIATE`，按顺序核验幂等键、归属、明确确认、随机凭据、摘要、有效期、申请状态及最新业务事实；之后检查同一订单是否已有待审核工单，最后把工单、申请状态、幂等结果、审计一次提交。
8. 再点一次相同请求，命中 `idempotency` 表里的原结果。换一个内容却复用相同键，会得到冲突。这就是“网络重试不会重复创建工单”的具体实现。

## 文件里分别放什么

| 文件 | 你要找到的核心内容 |
| --- | --- |
| `config.py` | `Config` 保存配置和可注入的时间函数；`from_env()` 读配置并拒绝不完整 Dify 配置或复用工具/用户密钥 |
| `db.py` | `SCHEMA` 定义存储；`Database.connect()` 管理事务及连接生命周期；`_seed()` 只在首次创建时按当天生成演示数据 |
| `service.py` | `_order()` 拿到有权限的订单；`_eligibility()` 核验规则；`public_policies()` 做公开政策筛选；`propose()` 生成申请；`human_preview()` 提供确认快照；`confirm()` 完成工单事务；`ticket()` 校验工单归属；`audits()` 读取当前用户日志 |
| `api.py` | Pydantic 请求模型、用户认证、工具认证、错误映射和路由；`tool_schema()` 只导出公开知识工具，`full_schema()` 提供业务文档 |
| `dify.py` | `chat()`：未配置上游就明确返回 `offline_rules`；已配置时调用 Chatflow HTTP 接口，超时/异常返回错误 |
| `static/index.html` | 用户操作顺序、确认勾选框、状态展示；用 `textContent` 显示不可信文本 |
| `tests/test_api.py` | 每条业务保证对应的可重复测试，不依赖 MySQL、Dify 或真实订单 |

`service.py` 的 `serialize()` 保证对象键顺序一致，`digest()` 才能稳定地计算 SHA-256。摘要不代替用户认证：它负责“确认的内容没变”，Bearer token 负责“谁在确认”，随机确认凭据绑定这一笔申请。

`_snapshot()` 只包含动作、订单、政策和退货原因，没有把实时的“已签收几天”写进摘要；确认时会重新计算是否仍符合退货条件。这样摘要绑定实际被批准的业务内容，时间推进也由规则重新判定。

`_audit()` 本身不主动提交，通常跟业务操作处于同一事务；订单读取被拒绝时，`order()` 会先提交拒绝日志再抛出异常，避免日志被异常回滚。这里记录的是明确实现的读取与申请/建单事件，不应宣传为完整生产审计体系。

## “接了 Dify”具体接在哪里

这份项目没有改 Dify 源码。扩展点有两个：

- Dify 可以导入 `/openapi.json`，调用 `public_policies()`；认证是独立的工具 token。这条路径没有用户身份，没有订单查询和写入能力。
- 本服务的 `/api/assistant` 在核验用户订单后，调用 `dify.py:chat()`，把已核验的规则结果与用户问题发送给你配置的 Chatflow。Chatflow 的回答只用于展示。

不能把共享 Dify token 配成 Alice 的用户 token，然后宣称“多用户订单安全”。这里在路由层分开认证，在 OpenAPI 层分开工具范围，在 Service 层再次按用户读取订单。Dify 回调也不能代替人的确认：工具文档根本不包含确认入口。

服务端调用 Dify 只用了 `httpx`。这有利于先学会 HTTP 输入、超时和错误处理，再决定是否需要更复杂的 SDK。当前不是向量 RAG；`public_policies()` 只是先筛选有效文档，再返回政策来源和命中的关键词。不要把开源平台原有的能力当成自己已经开发的功能。

## 你自己重写时的顺序

1. 先定义订单、政策、申请、工单的数据结构，明确一次业务请求的输入/输出。
2. 写 `_eligibility()` 这样的纯业务路径，先做正确的日期/状态/政策判断，不接模型。
3. 写归属校验和失败返回，再加路由。用别人用户的 token 测试，确认不能读到订单。
4. 写申请快照和确认流程，再把幂等表与工单写入放到同一事务里。
5. 补政策冲突、过期确认、旧快照、重复请求等反例测试；正常路径成功远远不够。
6. 最后才加入大模型解释，并让外部超时明确失败。没有模型时业务核验也应能演示。

## 三个动手练习

**练习一：给数码商品加一个“未拆封”条件。** 找到 `_eligibility()` 的拥有者，不要仅在 HTML 上隐藏按钮。为订单新增并持久化状态，修改核验逻辑，补一条拆封后不能申请的测试。确认旧申请碰到状态变化时被拒绝。

**练习二：让政策检索真正按相关性排序。** 先设计固定的 20 条问答和标准政策来源，用现有关键词版本跑基线，再接你选择的向量库/Embedding。记录命中率和错误案例，才有资格在简历写提升数据。

**练习三：增加撤销待审核工单。** 自己定义合法状态转换，检查用户归属，绑定工单版本，并防止并发撤销和审核冲突。完成后修改单订单活动工单唯一约束覆盖的状态，并补测试，而不是让模型直接改数据库字段。

## 面试时能讲清楚的四个问题

- 为什么模型不能自己判定退货？政策有版本、日期、订单归属和可验证的规则，需要服务端可重复执行。
- 为什么先生成申请，再确认？生成内容和执行操作是两件事，确认必须绑定具体订单、原因和政策，不能只保留一个全局 `approved=true`。
- 为什么还要数据库事务和唯一索引？只在代码里先查再建，两个并发请求可能同时通过；事务与数据库约束共同保证数据不重复。
- 为什么离线模式也有意义？它证明身份、规则、工单流转与模型供应商解耦，核心业务能够被本地测试验证；它不证明模型回答质量。
